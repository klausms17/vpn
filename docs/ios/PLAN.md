# Klaus VPN for iPhone: implementation plan (checked 26 Sep 2026)

**Status (27 Sep 2026):** phases 1 and 2 are done: the Go core builds for iOS (`ios.yml`, Linux) and the unsigned app plus packet tunnel compile on macOS (`ios-app.yml`). Phase 3 (signing) waits for the owner's Apple Developer account (section 8). Drafts for the later phases are in `docs/ios/drafts/` (not built): the App Store Connect profile tool, the panel manifest and Caddy snippet, ExportOptions, the UDID enrollment prototype and the `ios-devices.yml` draft.

## 0. Decisions in brief

- **Targets.** App `com.klausms.vpn` and packet-tunnel extension `com.klausms.vpn.tunnel` come first. A widget `com.klausms.vpn.widget` comes later.
  - App Group: `group.com.klausms.vpn`.
  - Minimum iOS 17.0, iPhone only (`TARGETED_DEVICE_FAMILY=1`).
- **Where Xray runs.** Inside the extension, on the utun file descriptor. Go's `TunnelFD()` finds it by scanning the process's fds. The private KVC key path is not used.
- **Build toolchain.**
  - Runner `macos-26` with `DEVELOPER_DIR=/Applications/Xcode_26.6.app/Contents/Developer`.
  - The project is generated by XcodeGen 2.46.0. The Go core is built as `Libxray.xcframework`, device slice only (ios/arm64), and cached.
- **Per push.** Each relevant push runs one Linux job and one macOS job.
  - Without secrets: an unsigned build for a generic iOS device.
  - With secrets: a signed archive exported with method `release-testing` (Ad Hoc).
- **Signing.** Manual signing. The Ad Hoc profiles are made on Linux by a small Go tool (standard library only) that calls the App Store Connect API. The Apple keys live only in GitHub secrets, never on the panel.
- **Adding a friend's iPhone.**
  1. The panel captures the UDID with a "Profile Service" configuration profile.
  2. The panel starts `ios-devices.yml` through `workflow_dispatch`.
  3. A Linux job registers the device and regenerates the profiles.
  4. A macOS job re-exports the stored `.xcarchive` (about 2 minutes).
  5. `klaus-panel publish-ios` publishes the result.
- **Android.** It is unchanged in behaviour. The only edits are an `ios/**` path ignore in `android.yml`, and Go changes that are either behind the `ios` build tag or have no effect on Android.

## 2. Architecture

**Processes.**

| Process | Links Libxray | What it does |
|---|---|---|
| `KlausVPN.app` (SwiftUI) | yes | Screens; editing the store; imports and pings **while the VPN is off**; installing, starting and stopping `NETunnelProviderManager`; sending messages to the extension |
| `PacketTunnel.appex` (`NEPacketTunnelProvider`) | yes | Owns the running `LibxrayController`. Builds the config from the store (so on-demand starts work without the app). Restarts when the network changes. Runs the supervisor (verify, failover, subscription refresh, block reports). Answers the app's messages. |
| `Widget.appex` (phase 8) | no | Reads `runtime.json`. Uses App Intents. Control Center toggle on iOS 18+. |

**Shared state** in the App Group container:
- `profiles.json`, the Go store. It uses the same schema as Android's `Models.kt` and a `flock` lock that is held for milliseconds, wrapped in `beginBackgroundTask`. A process suspended while holding a lock in a shared container is killed (crash code 0xdead10cc).
- `runtime.json`: status for the app and widget.
- `geo/`: geo databases downloaded by the app.
- `logs/{app,tunnel,crash}.log`.
- Device ID: a Keychain item with access group `group.com.klausms.vpn` and accessibility `kSecAttrAccessibleAfterFirstUnlock`, plus a copy in a group file.
- Do not use `identifierForVendor`. Apple says it can change with ad hoc installs, it differs between the app and the extension, and it is nil before the first unlock.

**How the processes talk to each other.**
- `NEVPNStatusDidChange` for status.
- `NETunnelProviderSession.sendProviderMessage` for request and reply, as JSON `{op: status|diag|probe|refresh|fetch|pin|reload}`.
- A Darwin notification `com.klausms.vpn.store-changed` tells the extension to re-read the store.

**Network rule (the main difference from Android).** On iOS only the extension's own sockets bypass the tunnel. Unlike Android's `addDisallowedApplication`, the containing app goes through it.
- VPN off: the app calls the existing Go functions (`MeasureOutboundDelay`, `FetchWithHeaders`, `PinCertificate`) directly.
- VPN on: the app sends the job to the extension. The extension uses `controller.probeOutbounds(…, parallel: 2)` or a direct fetch.

**Extension start sequence (`startTunnel`).**
1. `LibxraySetMemoryLimit(32<<20, 50)`.
2. `LibxrayInitEnv(geoDir)`: use the App Group `geo/` if it is valid and newer, otherwise the bundled `PacketTunnel.appex/geo`.
3. `LibxraySetCrashLog(group/logs/crash.log)`.
4. Read the store, then `LibxrayBuildConfig`.
5. Apply the settings from `LibxrayTunSettingsApple(ipv6)` with `try await setTunnelNetworkSettings(…)`.
6. Call `LibxrayTunnelFD()`. If it returns -1, throw an error with Russian text; the app reads it with `fetchLastDisconnectError` (iOS 16+).
7. `try controller.start(cfg, tunFd: fd)`.
8. Start the network watcher, memory watchdog and supervisor.

To restart on a network change or a settings change: set `reasserting = true`, `stop`, `start` on the same fd (Go dups it each time), then set `reasserting = false`.

**Tunnel settings** (Go returns them as JSON):
- `NEPacketTunnelNetworkSettings(tunnelRemoteAddress: "127.0.0.1")`, `mtu = 1500`. This must equal `TunMTU`, because Xray's read buffer is MTU+4.
- IPv4: `NEIPv4Settings(["198.18.0.1"], ["255.255.255.252"])`, `includedRoutes = [NEIPv4Route.default()]`, `excludedRoutes` = `bypassIPv4` minus `0.0.0.0/8`.
- IPv6: `fdfe:dcba:9876::1/126`, `includedRoutes = [2000::/3]`.
- DNS: `NEDNSSettings(["198.18.0.2"])` with `matchDomains = [""]`.
- Setting "exclude Apple 17.0.0.0/8" (push notifications), default on. Needs checking on a device.
- `includeAllNetworks = false`.

**Memory (50 MiB limit reported by Apple's forum engineer, not documented).**
- Go memory limit 32 MiB with GOGC 50 in steady state.
- GOGC 10 while `Start` runs, then back to 50, then `FreeOSMemory`.
- A Swift watchdog reads `phys_footprint` every 5 seconds and listens to the memory-pressure source. On a warning it calls `LibxrayReleaseMemory()`; on a critical event it restarts the core.
- The extension records its peak so the Diagnostics screen can show it.
- If `blocked_only` still peaks above about 45 MB on a device, shrink the gVisor TCP buffers. Xray hard-codes them in `stack_gvisor.go:27-32` (8 MiB receive / 6 MiB send maximum). Patch them only in the iOS build (`build-libxray-ios.sh` builds with `-modfile=ios.go.mod` plus a `replace` to a patched copy) and send the change upstream.

**What cannot be ported.**
- Per-app bypass needs MDM. Hide that screen. Keep ru_direct routing, and add a help screen for Shortcuts automations.
- The Quick Settings tile becomes a Control Center control (iOS 18, phase 8).
- There is no persistent notification. The extension posts errors with `UNUserNotificationCenter`.

## 4. Go changes in `libxray` (Android keeps working)

1. **`libxray/tunfd_ios.go`** (`//go:build ios`). Exported functions:
   - `TunnelFD() int32`: scans fds 0–1023 with `unix.Getpeername` and keeps `*unix.SockaddrCtl` whose `ID` matches `unix.IoctlCtlInfo("com.apple.net.utun_control")`. It confirms with `unix.GetsockoptString(fd, 2, 2)` that the name starts with "utun". Returns -1 if nothing is found.
   - `SetMemoryLimit(bytes int64, gcPercent int32)`.
   - `ReleaseMemory()`.
   - `TunSettingsApple(ipv6 bool) string`.

   Internal functions:
   - `prepareTunFd(fd)`: `unix.Dup` plus `unix.CloseOnExec`.
   - `startGC()`: GOGC 10 during Start, restored afterwards.
2. **`libxray/tunfd_other.go`** (`//go:build !ios`): `prepareTunFd` returns the fd unchanged, and `startGC` does nothing. This is why the AAR does not change.
3. **`libxray/libxray.go` `Controller.Start`:**
   - `fd, err := prepareTunFd(tunFd)`.
   - If `fd > 0`, `Setenv("xray.tun.fd")`; otherwise `Unsetenv`. Android's default is "0" anyway, so this is neutral there.
   - `defer startGC()()`.
   - Update the comments that mention only Android.
4. **`libxray/tunnet.go`:** add a pure `appleTunSettings(ipv6)` (excluded IPv4 routes as address plus mask, IPv6 included routes, DNS, MTU). `TunSettings` is unchanged. Android reads `TunConfig` with `AppJson { ignoreUnknownKeys = true }`, but nothing it reads is touched.
5. **Tests.**
   - `tunnet_test.go`, runs on Linux: excluded list = `bypassIPv4` minus `0.0.0.0/8`, and the masks are correct.
   - `tunfd_darwin_test.go` (`//go:build darwin && ios`), runs only on the macOS runner with `go test -tags ios -run TestTunFdSurvivesRestart .`:
     1. Use a `unix.Socketpair` end as a fake utun.
     2. Start with the tun inbound, then Stop.
     3. Run `runtime.GC()` three times.
     4. Check that `unix.FcntlInt(fd, F_GETFD, 0)` still succeeds.
     5. Start again.
     - **Uncertain:** the test may need to supply a name for `Name()`.
6. **`scripts/build-libxray-ios.sh`:**
   ```
   gomobile bind -v -target=ios/arm64 -iosversion 17.0 -trimpath \
     -ldflags='-s -w -buildid= -checklinkname=0' -o ios/Frameworks/Libxray.xcframework .
   ```
   gomobile's defaults are iOS 13.0 and `-fembed-bitcode` (`env.go:217,223`). After the build, if `otool -l` finds `__LLVM`, run `xcrun bitcode_strip -r`.
7. **`scripts/prepare-geo.sh`:** an optional second argument for the destination folder. The Android default is unchanged.
8. **`go.mod`:** `golang.org/x/sys` moves from indirect to direct after `go mod tidy`. Nothing else changes.
9. **Phase 5 port from Kotlin to Go**, used by iOS. Android stays on Kotlin until it is migrated one module at a time, optionally.
   - New files: `store.go` (`OpenStore`, same JSON as `Models.kt`), `subprep.go` (`PrepareSubscription`, `ParseUserInfo`, `IsStale`), `device.go` (`DeviceHeaders`), `importtext.go` (`ClassifyImport`, `PrepareLinks`, `DeepLinkPayload`), `failover.go`, `blockreport.go`, `appupdate.go` (`ParseAppUpdate(text, "ios")`), `geoupdate.go` (a `GeoProgress` interface).
   - Port each Kotlin test with it. `DeviceHeaders` must reproduce the exact recipe: SHA-256 of `"klausvpn-hwid-v1|"+raw`, first 32 hex characters. Use the vector from `DeviceHeadersTest.kt`.

## 5. CI design

**`android.yml`:** add `"ios/**"`, `".github/workflows/ios*.yml"` and `"server/remnawave/klaus_ios.py"` to `paths-ignore`. Nothing else changes.

**`ios.yml`:**
- Triggers:
  - `push`, all branches, on `paths: [ios/**, libxray/**, scripts/build-libxray-ios.sh, scripts/fetch-geo.sh, scripts/prepare-geo.sh, .github/workflows/ios.yml]`.
  - `workflow_dispatch` with inputs `register_udid`, `device_name` and `sign: auto|no`.
- `concurrency: ios-${{ github.ref }}` with cancel-in-progress.
- `defaults.run.shell: bash`, so failures inside pipes are not hidden.
- Skip the run if the commit message contains `[skip ios]`.

Job `prepare` (ubuntu-latest, 15 min):
1. `setup-go` with `libxray/go.mod`.
2. `GOOS=ios GOARCH=arm64 CGO_ENABLED=0 go build .` and `GOOS=darwin GOARCH=arm64 CGO_ENABLED=0 go vet -tags ios .`.
3. `go test ./...` in `ios/ci/asc`, against the mock API.
4. `scripts/fetch-geo.sh geo-upstream && scripts/prepare-geo.sh geo-upstream ios-geo`, uploaded as artifact `ios-geo`.
5. Output `core_key = hashFiles('libxray/*.go','!libxray/*_test.go','libxray/go.mod','libxray/go.sum','scripts/build-libxray-ios.sh')`.
6. Signing gate: if `ASC_KEY_P8`, `IOS_DIST_P12_BASE64` and `vars.IOS_TEAM_ID` are all set:
   - Read the certificate serial with `openssl pkcs12 -legacy -nokeys | openssl x509 -noout -serial`.
   - Run `go run ./ios/ci/asc doctor`.
   - Run `go run ./ios/ci/asc profiles --bundle com.klausms.vpn --bundle com.klausms.vpn.tunnel --cert-serial … [--register UDID=NAME] --out profiles`.
   - Upload artifact `adhoc-profiles` (retention 1 day; the files contain UDIDs).
   - Outputs: `signed`, and the profile UUIDs.

Job `ios` (`macos-26`, 30 min, needs `prepare`):
1. **Get the xcframework.**
   - `actions/cache@v6` with key `libxray-ios-<Xcode build>-<core_key>`.
   - On a miss: `gh release download libxray-ios-cache -p Libxray-<key>.zip`. A release asset does not expire and every branch can read it; actions/cache is per branch and dropped after 7 days unused.
   - On a miss there too:
     1. `setup-go`.
     2. `go test -tags ios -run TestTunFdSurvivesRestart .`
     3. `scripts/build-libxray-ios.sh`, with the bitcode check.
     4. Upload the result to both caches.
2. Download `ios-geo` into `ios/PacketTunnel/Resources/geo`.
3. Install XcodeGen from the 2.46.0 zip, checking the sha256 `4d9e34b62172d645eed6457cac13fc222569974098ef4ee9c3368bedf0196806` (verified here), then `xcodegen generate --spec ios/project.yml`.
4. **Without secrets:**

   xcodebuild build -project ios/KlausVPN.xcodeproj -scheme KlausVPN -configuration Release \

   - `codesign --verify --deep --strict`.

   - `security cms -D -i embedded.mobileprovision`: device count ≥ 1 and the expiry date.
   - The geo files are inside the appex.
   - No `__LLVM` section; print the sizes.
7. **Release `ios-build-<branch>`** (deleted and recreated, like Android's `build-<branch>`):
   - `KlausVPN-1.0.N.ipa`

**`ios-devices.yml`** (`workflow_dispatch` with inputs `devices` (JSON, at most 5), `release_tag` and `dry_run`; concurrency `ios-devices` without cancelling):

  2. Keychain, profiles, `export.sh`, `verify-ipa.sh`.
  3. Replace the `.ipa`, `SHA256SUMS.txt` and `ios.json` in the release. The version and build stay the same; `profileRev` goes up by one. Existing friends are therefore not asked to update.

## 6. Signing and the `ios/ci/asc` tool (Go standard library only, runs on Linux)

- **Token:** ES256 JWT with `kid`, issuer, lifetime of 20 minutes or less, audience `appstoreconnect-v1`.
- **`doctor` checks:**
  - The key works.
  - The bundle IDs exist, and `GET /v1/bundleIds/{id}/bundleIdCapabilities` includes `NETWORK_EXTENSIONS` (app and tunnel) and `APP_GROUPS` (all).
  - A `DISTRIBUTION` certificate exists whose `serialNumber` matches the p12.
  - Warnings when the certificate or a profile has fewer than 30 days left.
  - How many of the 100 iPhone slots are used.
- **`register`:**
  - `GET /v1/devices?filter[udid]=…`, then `POST /v1/devices` with `platform: IOS`.
  - It never disables or re-enables a device, because disabling one invalidates every profile that contains it.
- **`profiles`:**
  - Enabled devices with `deviceClass == IPHONE` (not filtered by platform, because the platform filter also returns `UNIVERSAL`).
  - Reuse an existing profile if its `profileState` is ACTIVE, it has more than 30 days left and its `ProvisionedDevices` (read from `profileContent`) equal the enabled set.
  - Otherwise `POST /v1/profiles` with `IOS_APP_ADHOC` and the relationships `bundleId`, `certificates` and `devices`, then `DELETE` the older ones.
  - Before any macOS minute is spent, check that the profile's `Entitlements` include `packet-tunnel-provider` and `group.com.klausms.vpn`. If not, fail with the message "assign the App Group in the portal".

## 7. The panel side (`server/remnawave`)

**`klaus-monitor` container,** internet-facing and without GitHub or Apple tokens. It gets a new rw volume `./ios:/data` (uid 65534, files mode 600) and read-only `./app`.

- `GET /klaus/ios/enroll?u=<subscription URL>`:
  - Take the shortUuid from the last path segment and require an ACTIVE subscription (`subscription_ok`).
  - Limits: 6 tries per subscription per hour, at most 2 iPhones per subscription, 95 in total.
  - Create a single-use challenge valid for 15 minutes.
  - Answer with the unsigned Profile Service profile: `Content-Type: application/x-apple-aspen-config`, `DeviceAttributes` = UDID, PRODUCT, VERSION.
- `POST /klaus/ios/udid` (at most 64 KB):
  - Parse the CMS (DER or BER), read the plist, check the challenge and the UDID format.
  - Add the device to the queue, then answer `301` with `Location: https://SUB/klaus/ios/done?t=<ticket>`. The UDID never appears in a URL.
  - Send a Telegram notice without the UDID, for example "iPhone17,1 iOS 26.5 от masha, 23/100".
- `GET /klaus/ios/done?t=` and `GET /klaus/ios/install?u=`: a Russian status page.
  - It shows "Готово" when the device's hash is in `version.json.deviceHashes`.
  - The install link: `itms-services://?action=download-manifest&url=<percent-encoded https://SUB/app/ios/<random>/manifest.plist>`.
  - It includes the Safari-only note and the Developer Mode steps.

**Host `klaus-panel`** (root-only config holds `GITHUB_TOKEN` and a new `GITHUB_ACTIONS_TOKEN`):
- `ios-setup`: reads the Actions token with a hidden prompt.
- `ios-sync`: started by a systemd `.path` unit on `ios/queue.json` and a 15-minute timer.
  1. Approves (automatically unless `IOS_AUTO_APPROVE=0`).
  2. Sends up to 5 devices to `POST /repos/klausms17/vpn/actions/workflows/ios-devices.yml/dispatches` with `ref` = the published branch and `X-GitHub-Api-Version: 2026-03-10`.
  3. Polls the run, then calls `publish-ios`.
  4. After registration, keeps only `sha256(UDID)`.
- `publish-ios [--tag]`, modelled on `cmd_publish_apk`:
  1. Check the SHA256.
  2. Put the IPA in `/srv/app/ios/<random>/KlausVPN.ipa` and `manifest.plist` next to it. The manifest has `software-package`, `display-image` 57 and `full-size-image` 512, `bundle-identifier`, `bundle-version`, `kind=software` and `title`.
  3. Write `/srv/app/ios/version.json` = `{build, version, expires, install:"https://SUB/klaus/ios/install", deviceHashes}`.
  4. Remove the previous folder after 13 hours.
- `ios-devices`: counts only, never UDIDs.
- `ios-add-udid NAME UDID`: manual fallback.
- `ios-approve TICKET`.
- Default tag: `ios-build-claude-compassionate-mayer-6jph8m`, because `publish-apk` currently publishes from that branch. It can be changed with `IOS_RELEASE_TAG`.

**`install-panel.sh` (Caddy):**
- In `handle /klaus/*`: `request_body { max_size 64KB }` and `reverse_proxy klaus-monitor:8080 { request_buffers 64KB }`. The phone's POST may arrive without Content-Length; Caddy adds it once the body is buffered.
- In `/app/*`: `@ipa path *.ipa` → `application/octet-stream`, and `@plist path *.plist` → `text/xml; charset=utf-8`.
- With `CADDY_TLS=internal`, refuse iOS features: both itms-services and Profile Service need a publicly trusted certificate.

1. "Откройте страницу в Safari" (Telegram's in-app browser cannot install these).

## 10. Risks and unknowns (most serious first)

1. **Apple can revoke the certificate or the account.** Ad Hoc is meant for testing on registered devices. Handing it to friends is a grey area under the Program License Agreement. A revocation stops every install at once.
2. **The profile and certificate expire yearly.** When they do, the app stops launching. CI warns 30 days ahead. Renewal steps:
   1. Make a new distribution certificate from a new CSR.
   2. Update the secrets.
   3. Rebuild and publish.
   4. Friends update from the in-app card.

   There are 100 iPhone slots per membership year. Disabling a device does not free its slot. Pause automatic registration around the renewal and use the portal's device reset offered at renewal.
3. **Developer Mode.** It is unclear whether it is required and whether its switch appears without a computer. If the switch is hidden, `idevicedevmodectl reveal` (libimobiledevice) from a PC may help; this is unverified.
4. **The utun fd lookup is not supported by Apple.** Every major client relies on it. Fallback: a `socketpair` bridge from `packetFlow` (more copies, untested).
5. **The 50 MiB limit** (not documented for iOS 27). `blocked_only` peaks at 42–46 MB in the Linux measurements, before Swift/NetworkExtension overhead and before gVisor. The start-phase GC and the buffer patch are the levers.
6. **DNS from the extension.** Xray's "localhost" DNS entry uses the system resolver. Whether the extension's own DNS lookups stay out of the tunnel is not documented. If they don't, resolve server names in Go before applying the tunnel settings.
7. **The first launch checks with Apple's server** (ppq.apple.com), which needs internet and was down on 10 March 2026. The Profile Service needs Safari and a public certificate; Lockdown Mode blocks it, and Stolen Device Protection behaviour is unverified. The 301 redirect has to be tested on iOS 26/27.
8. **Every friend's UDID is inside the IPA** in plain text. Serve it only from the random per-release folder, and tell friends.
9. **Minutes.** The 10× factor is unconfirmed in GitHub's current docs. The caches are per branch with 7-day expiry, which is why there is a release-asset fallback. Linux re-signing stays unproven (rcodesign has had no release since Nov 2024).
10. **Smaller unknowns:**
    - Deleting a profile should not affect apps already installed with it. Test with two phones.
    - Whether a widget can use `NETunnelProviderManager` without the Network Extension entitlement.
    - The Russian label on `PasteButton`.
    - Whether `CODE_SIGNING_ALLOWED=NO` silences manual signing in the Release config.
    - The exact 409 error text when the 100-device cap is reached.
